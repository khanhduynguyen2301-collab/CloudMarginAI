# CloudMargin AI — Workload & Cost Model (Phase 1)

Status: draft for review · Source: Blueprint v1.2, Section 6 (Data sources), Section 7 (economic model), Section 8 (feature families)
Phase: 1 (Data simulator) · Weeks 3–5

This defines what the "clean" (non-incident) 90 days of history looks like before `phase1-incident-injection-spec.md` perturbs it. If detection can't beat a seasonal-naive baseline on this clean data, the incidents were never the hard part — so this model has to be realistic enough to be genuinely forecastable, not trivially flat.

## Economic model (Section 7, applied)

Every `billing_hourly` row is generated the same way the blueprint says real cost should be read: **usage × effective unit price**, decomposed per service and SKU rather than as one lump number. The simulator never invents a cost directly — it always derives `effective_cost` from a `usage_amount` that some workload or capacity generator produced, so cost and utilization stay causally linked (this is what root-cause ranking in Phase 3 needs to have something real to find).

## Feature families generated

| Family | Generated here | Feeds |
|---|---|---|
| Demand | requests, active customers, transactions | `application_activity_hourly` |
| Capacity | instances, CPU/memory/GPU utilization | `resource_metrics_hourly` |
| Efficiency | derived at feature time in Phase 2 (requests/instance, queries/request) — not stored raw here | — |
| Reliability | error_count, latency_p50/p99 | `resource_metrics_hourly` |
| Change events | deployments, resource_changes | `deployments`, `resource_changes` |
| Cost | usage_amount, credits, effective_cost per SKU | `billing_hourly` |
| Temporal | hour, weekday, lag features | computed by Phase 2 from `hour`, not stored here |

Unit economics (cost/request, cost/customer) and temporal lag features are explicitly **not** generated by the simulator — they're Phase 2's `features_hourly` job, per `phase0-schema-v1.md`. Keeping them out of Phase 1 stops the simulator from silently pre-computing the thing Phase 2 is supposed to prove it can compute.

## Demand generation (`application_activity_hourly`)

**Decision — diurnal + weekly + trend + noise, no holiday calendar in v1:**

```
requests(h) = base_rate(service)
            × daily_curve(hour_of_day)      # smooth peak ~09:00–17:00 local, trough overnight
            × weekly_factor(day_of_week)    # weekend ≈ 0.55–0.7× weekday, per service
            × (1 + growth_rate)^(day / 7)   # gentle week-over-week growth
            × lognormal_noise(σ_demand)
active_customers(h) ≈ requests(h) / avg_requests_per_customer(service), with its own smaller noise term
transactions(h) = requests(h) × conversion_rate(service)
```

- `growth_rate`: **0.5%–1.5% per week**, service-dependent — small enough that a 8% cost jump with flat demand (Phase 0's "dangerous" example) is clearly abnormal, large enough that a naive flat baseline is measurably worse than a trend-aware one.
- Holiday/promo calendar effects are **deferred**, matching Phase 0's scope table treating anything beyond the core four incident families as out of v1 — a documented limitation, not an oversight.
- `active_customers`, `revenue`, and `plan` are populated except `revenue`, which stays null per Phase 0's deferred finance outcome.

## Capacity & reliability generation (`resource_metrics_hourly`)

**Decision — capacity tracks demand through each service's autoscaling policy, not independently:**

```
target_utilization(service) = 0.55–0.70          # policy setpoint, varies by service
instance_count(h) = ceil(requests(h) / (capacity_per_instance(service) × target_utilization))
                     , bounded by [min_replicas(service), max_replicas(service)]
cpu_utilization(h) = requests(h) / (instance_count(h) × capacity_per_instance(service)) + noise
latency_p50/p99(h) = base_latency(service) × congestion_factor(cpu_utilization) + noise
error_count(h)     = requests(h) × base_error_rate(service) (Poisson), rising only under injected incidents
```

`ml-training-job` (the idle-accelerator incident's home) is the one service whose `instance_count` and GPU utilization are **not** demand-driven — it runs on a fixed job schedule, which is exactly what makes an idle accelerator (compute running, utilization near zero) a detectable anomaly rather than noise.

## Change events (`deployments`, `resource_changes`)

**Decision:**
- `deployments`: each service releases on an independent Poisson-ish cadence, mean **1 deployment per 6–9 days**, `version` monotonically incrementing, `changed_component` drawn from {api, worker, config, dependency}.
- `resource_changes`: background rate of **1 benign config change per service per ~20 days** (label/tag edits, non-incident-causing) so that "a change happened near this time" is not, by itself, evidence of an incident — the root-cause ranker (Phase 3) has to be discriminating, not just change-adjacent. Incident-causing changes are injected separately and are documented in `phase1-incident-injection-spec.md`, not here.

## Cost model (`billing_hourly`)

**Decision — fixed, documented per-SKU unit price table (illustrative GCP-like rates, not real GCP pricing):**

| SKU | Usage unit | Unit price (USD) | Driven by |
|---|---|---|---|
| `compute.vcpu-hour` | vCPU-hour | $0.031 | `instance_count × vcpu_per_instance` |
| `compute.gpu-hour` | GPU-hour | $2.10 | `ml-training-job` instance schedule |
| `storage.standard-gb-month` | GB-month (hourly fraction) | $0.020 / 730 | slow-growing per service |
| `network.egress-gb` | GB | $0.085 | correlated with `requests` |
| `logging.ingested-gb` | GB | $0.50 | correlated with log verbosity level (the logging-regression lever) |
| `db.cpu-hour` | vCPU-hour | $0.096 | `checkout-api`'s backing database (the query-regression lever) |

`effective_cost(sku, h) = usage_amount(sku, h) × unit_price(sku) × (1 − credit_rate)`, with `credit_rate` at a small flat sustained-use-style discount (e.g. 3%) applied uniformly so it doesn't create a spurious pattern. `credits` and `effective_cost` are stored separately per the schema; `currency` is always `USD` for v1 (multi-currency is out of scope, consistent with single-cloud-first).

Cost noise is multiplicative lognormal, calibrated small (σ ≈ 0.03–0.05) — large enough that a naive point forecast is imperfect (so prediction intervals mean something), small enough that a 3-hour, guardrail-crossing anomaly is still cleanly separable from noise, per the anomaly policy's "≥3 consecutive hours + material $ threshold" rule.
